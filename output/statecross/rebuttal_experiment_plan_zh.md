## 1. 结论

**论文有可以成立的 benchmark contribution，但目前的证据尚不足以完整支撑三项贡献。本轮先增加真实代码行为、文件信息通道和诊断修复的证据；旧主实验的有效性限制单独说明，暂不以完整重跑占用优先预算。**

现稿较可靠地说明：在给定模板、候选程序和接口下，不同记忆配置产生不同的执行正确率；在特定固定决策实验中，完整历史或当前状态条件下的正确率点估计明显更高。现稿尚不能充分说明：低分主要源于长程状态记忆；诊断阶段就是行为错误的因果来源；某个记忆系统普遍最好；任务已覆盖广义的软件工程或独立任务族。

这是评测论文，核心证据应回答三个问题：**测到的是否是目标能力、测量是否有额外价值、比较是否可信且可复现**。增加模型或系统数量，不能替代这些验证。

## 3. 最可能影响 rebuttal 的证据缺口

### 3.1 旧主实验的解释限制：old-valid 候选措辞

论文明确承认：旧方案仍然有效时，候选描述已经把它称为 withdrawn。七系统合计 4,144 个 old-valid 决策中只有 17 个正确；各系统该条件正确率为 0.14%–0.80%。这使“无法跟踪时间状态”与“遵从了错误候选说明”难以区分。

**只删除 old-valid 行、改报 B3、在固定 checkpoint 重新评分，都不能修复原始完整轨迹。** 之前的错误选择会影响后续文件、执行记录和记忆。

如果后续要用这部分结果支撑长程记忆失败的强结论，仍需修正接口并重跑完整轨迹。在此之前，保留其局限、不强化该结论。本轮暂缓这项完整重跑，先执行 E7/E3/E2；新实验不依赖旧主表已被修复。结果未必一定改善，不能提前写结论。

来源：[四条件结果](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:204)；[作者对局限的明确说明](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:297)。

### 3.2 总准确率存在多数动作捷径，不能只与 25% 随机比较

离线 checkpoint 标签参照中，“永远选新离线方案”准确率为 45.83%；主表最高 MemOS 为 47.40%，二者点估计仅差 **1.57 个百分点**。不过前者是离线常量参照，后者是在线完整轨迹，不能把这个差值当作已完成的配对在线优效检验。

这并不说明 benchmark 没有区分力：MemOS balanced accuracy 为 44.33%，常量策略为 25%。它说明论文需要把**四条件 balanced accuracy 与分条件表现放到主要位置**，并加入实际在线捷径基线。也不应直接更改事件分布以追求漂亮分数；若新增类别均衡版本，应明确它是新设置。

来源：[主表](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:184)；[常量动作参照](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:505)。

### 3.3 九任务×一次运行，支撑不了稳定的系统总排序

主实验是每个系统每个任务一次。16,128 个决策不是 16,128 个独立样本。GraphRAG 在 5/9 个任务上高于 MemOS；移除 task 3010 后二者均值排序反转。

重复运行用于估计同一任务内的随机波动；新增独立任务/任务族用于估计任务泛化，两者不能互相替代。不要把三次重复乘九任务当作 27 个独立任务，也不要围绕 Holm-adjusted p 从 .055 到 .047 组织 rebuttal。

来源：[实验规模](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:133)；[排名敏感性](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:229)；[统计方法](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:413)。

### 3.4 workspace 的核心作用没有被当前对照充分证实

六任务文件可见性实验：visible 50.91%、hidden 50.00%，差值 +0.91 pp，探索性区间 [-3.84, +5.66]。三任务改善、三任务下降。这不能证明文件可见有稳定收益，也不能证明 workspace 不重要。

hidden 条件仍有当前会话、候选动作、执行环境和 state hashes。需要检查这些渠道是否已经足以推断状态；同时，当前文件对照没有识别文件与显式记忆之间的互补关系。

来源：[workspace 对照](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:615)。

### 3.5 诊断汇总不等于行为错误的因果解释

历史 memory inventories、retrieval traces 和 paired diagnostic inputs 未恢复，生命周期数字从保留汇总重建。MemOS provenance 是 inferred。488 个 required-state occurrences 依次剩余 467 stored、254 retrieved、135 exposed；这里的 60.3% 是缺失 occurrence 中落在 retrieval 阶段的比例，**不是 60.3% 的行为错误由 retrieval 导致**。

替换控制中 Flat 与 A-MEM 的 primary flip rate 与 sham 相同；字符长度匹配也不等于 token 匹配。动作改变本身既可能有益也可能有害。完整证据与错误动作同时出现，能支持“证据已给出仍答错”，不能单独证明模型使用过记忆或隔离了内部推理机制。

来源：[诊断汇总](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:261)；[生命周期](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:743)；[替换控制](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:841)；[日志局限](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:297)。

## 4. 建议补的实验：设计、指标和判读

### E1｜后续暂缓：修正候选接口 + 完整轨迹重跑 + 反捷径测试

**要回答：benchmark 测的是状态遵循，还是候选措辞/位置偏好？**

设计：

- 将候选描述改为真实、静态的程序行为说明，移除与当下有效性冲突的 withdrawn 等措辞。保留理解程序所需的信息。
- 程序 ID 使用不携带答案的标识，候选顺序独立于正确状态随机化；ID 变化后正确答案按程序身份重新映射。
- 先在少量任务验证 checker 与 gold 映射；随后使用新版本重跑完整轨迹，固定版本、API route 和调用配置。
- 固定 checkpoint 做两类配对：①语义等价改写/顺序置换，gold 程序身份保持；②改变生效时间、撤回事件或作用域，产生 gold 改变的反事实。后者必须同步维护相关历史/文件的一致性。
- 同协议跑 always-new、latest-message-only，以及真正可运行的状态账本基线；离线常量参照单独列出。

报告：balanced accuracy、四条件准确率、配对 task gain、cycle/drift；等价改写一致率与“配对两题都答对”的比例；反事实两题都答对的比例。单纯翻转答案不等于正确理解变化。

判读：若中性改写后原来的困难和系统差异保留，构念证据增强；若多数困难消失，应修改难度与失败来源叙述。无论哪种结果，均不能保留错误界面作为主实验依据。

### E2｜紧随 E7/E3：新鲜日志 + 失败环节修复

**要回答：diagnostics 是否可复核，是否能指导有效修复？**

设计：

- 新运行保存 write/update、inventory、候选检索集、rerank、最终输入、action、checker 和来源映射。评测侧维护 immutable state/event ID；不给 agent 泄漏 gold。
- 对“已存储/已检索/已暴露”匹配做盲审；明确 exact、inferred、语义等价和不确定样本。报告标注数量、分歧及一致性，不把启发式匹配视为真实标签。
- 在同一 checkpoint 对最早缺失阶段做单阶段 oracle repair：补 storage 后重跑后续检索；补 retrieval 后重跑选择；补 exposure 时保持最终上下文预算。使用真实来源中的必要证据，标明 oracle 修复仅用于诊断上界。
- 同时做 token、位置、记录数匹配的无关信息 sham 和语义等价改写控制；确认预算上限及不可完全匹配的部分。
- 比较诊断所指向的修复与匹配的非目标修复。固定输入；如 API 有随机性，使用重复调用估计波动。

报告：wrong→correct、correct→wrong、净准确率变化，以及按 task 聚合的不确定性；报告每个阶段的明确分母。不能用不同分母的 flip 指标直接相减。

判读：目标修复相对控制有更强、可重复的正确率改善，才支持“诊断能指导干预”。若无改善，应保留为证据覆盖描述，进一步检查标注、证据充分性及 policy 使用能力，不把覆盖缺失直接写成原因。

**因果验证的直白版本：**先从一次失败轨迹中找出最早断掉的一环；从出错前的同一个检查点重新开始，只补这一环，再让 agent 自己继续完成后续动作。比如诊断为“记忆里没有存到新要求”，修复组只补进这条要求；对照组补入等长但无关的信息。若修复组后续真实任务成功率更高，且重复后仍如此，才有证据说“修这个环节能改善表现”。不能只展示修复后答案变对，也不能同时把存储、检索、提示词都改掉，否则不知道是哪项起作用。

修复效果要报告两种结果：第一，修复后是否正确执行；第二，完整项目检查是否通过。修复阶段使用 oracle 补信息属于诊断干预，需明确标成“可修复性上界”；再补一个由 agent 自己完成该阶段修复的版本，才说明方法在实际系统里可用。

### E3｜第一批优先：重做文件可见/隐藏，再扩展文件 × 显式记忆四条件

**要回答：显式记忆与文件信息何时互补、何时冗余？**

| 条件 | 文件内容 | 显式记忆输入 |
|---|---|---|
| A | 可见 | 无 |
| B | 可见 | 有 |
| C | 隐藏 | 无 |
| D | 隐藏 | 有 |

先在保存的相同 checkpoint 上比较急性输入效果：固定任务状态、请求、候选和历史来源，分别屏蔽文件内容或记忆块，不重新生成另一个任务。检查文件名、hash、候选描述、固定周期是否泄漏正确动作。

主要对比：可见时记忆收益 B−A；隐藏时记忆收益 D−C；交互项 `(B−A)−(D−C)`。按 explicit/derivable/absent workspace information 分层；每层目前只有少量任务，不能把层内决策当成大量独立实例。

再选择核心系统做独立完整轨迹，评估长期累积效果。固定 checkpoint 的输入效果和长期系统效果分别报告；隐藏文件内容并不等于取消执行工作区。

判读：互补、冗余或模型未利用文件都是可能结果。若文件作用仍弱，应把贡献收窄为该信息设置下的比较，不能宣称已证明 workspace 普遍有益或无益。

现有文件可见/隐藏实验已完成一轮（6 个任务、每个条件每任务一次；共 12 条轨迹），结果为 50.91% 对 50.00%，终局通过均为 0/6。后续应当增加独立重复和任务数，并报告每个任务的配对差异和区间；**不应要求两组结果必须不同**。若增加样本后差异仍接近零，结论就是在当前任务和设置下未观察到文件可见性的稳定影响；若差异拉开，再看跨任务和重复是否一致。不能为了证明文件有用而只挑可见组获胜的任务。

建议先做同一批任务、同一批检查点的可见/隐藏配对重跑，减少任务状态差异；随后在新的独立任务实例上重复。每个条件至少 3 次独立运行可作为起点，但任务数和重复数应按成本与观察到的波动继续增加。若目标是证明文件与显式记忆互补，仍需完成上面的 2×2 四条件；单纯可见/隐藏比较只能回答“当前配置下显示文件有没有帮助”。

### E7｜第一批优先：真实项目修改与测试通过

**要回答：agent 是否能把跨会话要求落实到真实代码和项目状态，而不只是选对预设动作？**

用真实软件仓库中的小型、可复现任务：agent 先读需求并修改代码；中途开启新会话，再给出一条有生效时间或作用范围变化的新要求；agent 需要检查已有实现、更新文件并运行项目测试。任务应有可启动的仓库快照、明确的初始状态、可自动运行的测试和独立评分脚本。优先选真实 issue 或从真实 issue 改成可控任务，不让答案直接出现在任务说明、文件名或测试输出中。

首轮固定同一个 SWE-agent、模型和源码访问权限，比较“每会话重置、只保留代码工作区”与“每会话重置、保留代码工作区＋显式记忆”两组；完整历史组如增加则单列。每个任务从同一仓库快照开始，条件间配对，顺序随机或预先平衡，并做独立重复。保留提交 diff、命令记录、测试日志、会话间状态和 agent 的最终说明。

E3 在现有受控任务重做文件内容通道的可见/隐藏。真实仓库中源码仍应可读可改；若扩展文件对照，只屏蔽明确定义的历史需求载体，并检查 shell、搜索、Git 历史等旁路，单独报告协议。不能把整个仓库不可读与正常代码修改当作只差一个信息条件的比较。

主要指标用真实行为结果：隐藏测试是否通过、旧功能回归测试是否通过、要求变更是否只影响指定文件/模块、最终仓库是否可构建。辅助指标再报行动正确率、运行测试次数、人工修补量和耗时。不要把“agent 说自己完成了”当作成功。

为了把“为什么失败”连到“修复后是否变好”，从首轮起保存完整阶段日志和可恢复的检查点。预先固定失败样本纳入规则；从同一个失败前检查点分支，比较原样继续、单阶段修复和 sham，然后继续让 agent 实际改代码并跑测试。检查点包含代码、记忆及索引、会话/工具状态和相关输入；只恢复初始仓库不是恢复失败前状态。这样可以检验修复是否改善真实项目结果，而不仅是改善下一次选择题答案。

**当前实现状态：**`lhmsb.realworld` 已能创建独立 Git 工作副本、逐会话调用外部命令、运行评分命令并保存 diff/结果；尚未接通 SWE-agent 记忆读写、实际文件屏蔽和上述检查点修复。已有 3 项框架测试通过记录，不是真实 agent 实验结果。正式运行前必须分别验证这些控制生效，隐藏评分器在 agent 运行期间不可访问。

**范围控制：**先做 3–5 个不同机制的真实仓库任务，每个任务每条件至少 3 次，作为可行性实验；若要支撑广泛 SWE 能力主张，需要更多独立仓库和任务，不能把重复运行当成新任务。若当前轮次资源有限，先证明完整流程可复现，再扩规模。此实验可支撑“跨会话要求影响实际软件修改”的主张；它本身不能证明覆盖了所有 SWE-agent 能力。

### E4｜P1：非 oracle 状态账本 + 原生/公共选择对照

**要回答：现有系统收益是否超过简单可部署方案；排序是否由 adapter/selector 决定？**

基线账本由 agent 仅根据可见指令与历史维护，字段可包括对象、版本、有效时间、作用域、撤回/取代状态和来源。不得直接读取 evaluator 的当前 gold state；oracle current-state 仍作为单独上界。

对核心系统比较 native selection 与 common reranker，约束相同的最终输入 token 预算，并分别报告写入/检索/重排成本。五条记录不等于相同 token 或计算成本。若考察顺序，固定 record identity；若考察子集，控制排序规则。

现有固定决策对照已经显示 common selection 对 MemOS 为 +13.33 pp、对 Mem0 为 −8.89 pp、对 A-MEM 为 −6.67 pp，而且记录身份与顺序同时变化。因此新实验应进一步拆分，不应声称论文完全没有 selector 对照。

判读：若简单账本强，benchmark 仍可成立，但系统结论应强调有效状态表示和集成，而非复杂记忆架构的必要性。系统比较应明确是所测试整体 pipeline 的表现。

来源：[现有 native/common 结果](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:803)。

### E5｜P1，对广义泛化主张尤其重要：新结构任务族 + horizon 控制

**要回答：是否只适用于一个四动作事件模板；困难是否来自跨会话保留？**

新增 2–3 个机制不同的状态图，每类多个独立实例。例如：多个对象具有相互独立的时间线；具有嵌套覆盖与恢复的权限图；依赖条件与审批事件共同决定生效的流程。判定标准是 gold 状态转移结构改变，不是仅改项目名字或换时间戳。必须核对与现有生成器的区别。

固定 horizon 后比较不同结构；再将 reset 数、历史负载、距相关事件的间隔分别变化。可先做两个受控子实验：总事件/总决策数相同而 reset 次数不同；reset 数相同而无关历史量不同。避免一次改变所有变量后归因于 horizon。

加入 no-reset/full-history 与 no-change 对照，说明在静态任务也差、仅 reset 后差，还是状态更新特有的困难。统一指标；超出上下文预算的 full-history 要单独说明可行范围。

如果坚持“代码生成/广义工程 agent”贡献，再补小规模自由工具执行/代码修改任务，并按实际执行效果评分。若定位维持“选择预定义程序以遵循变化约束”，自由生成不是本轮必须项。

### E6｜低成本、高信息量：证明轨迹指标的增量价值

**要回答：drift/cycle 是否提供 accuracy 之外的解释？**

现有 cycle 是连续四步的局部一致性，不能独自证明长期遵循。drift 只有在之前正确遵循过同一 requirement lineage 时才 eligible；不同系统分母会变化，原始 drift count 不能直接公平排序。

从新鲜轨迹中寻找或预先构造总体准确率接近、错误时间结构不同的配对，展示 cycle、跨 reset 的保留/复发、首次失守时间能否区分。配合真实轨迹案例；合成序列仅作指标单元验证，不能替代系统实验。

报告 eligible numerator/denominator、分会话曲线和相同可比较决策集合的敏感性结果。低 drift 可能来自尚未形成早期 adherence，故必须与总体准确率一起解释。

来源：[指标定义](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:143)；[drift 分母与 cycle 范围](/Users/yiding/code/BEAM-LongHorizonMemBench/output/statecross/source_snapshot.tex:400)。

## 6. 如果 rebuttal 只能补三组结果

**第一组：E7 真实仓库跨会话改代码。** 让同一个 SWE-agent 在会话重置后继续处理需求变化，比较仅工作区与工作区＋显式记忆，按隐藏测试、回归测试及指定作用范围评分。

**本轮不把 E1 完整重跑塞回前三项，也不把它设为新实验前置。** 旧措辞问题继续作为限制说明；新证据仅支撑实际测试过的仓库、任务和配置，不追溯性地修复旧主表。
