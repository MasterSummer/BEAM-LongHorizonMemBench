# StateCross 补充实验设计计划

更新日期：2026-10-28。按本轮决定执行：**先做真实仓库跨会话改代码和文件可见/隐藏，再做失败环节修复。旧主实验的候选措辞修正后完整重跑暂缓，不作为这三组实验的前置条件。**

## 目的

本计划补足三类证据：

1. agent 能否在真实代码仓库中跨会话处理要求变化，并通过项目测试；
2. 项目文件可见或隐藏是否会影响表现，以及它和显式记忆是否互补；
3. agent 失败后，修复被诊断出的环节能否让任务表现变好。

本计划不预设实验结果。若两组没有稳定差异，也应如实报告。

| contribution，用直白的话说 | 已经有什么 | 本轮补什么 | 为什么补 |
|---|---|---|---|
| C1：测 agent 换会话后，能否继续按变化的要求做事 | 受控任务中选择并执行预设程序；9 任务主比较；accuracy、cycle、drift | **第一优先：真实仓库跨会话改代码**，由独立测试检查新需求、旧功能和作用范围 | 现有主结果没有证明 agent 能自己读仓库、写补丁并把变更做对 |

## 实验一：真实仓库中的跨会话修改

**问题：**agent 能否把跨会话的要求和变更落实到代码，而不只是从预先写好的选项中选答案？

**任务：**选取 3–5 个真实软件仓库任务作为第一轮可行性实验。优先从真实 issue 或维护需求中选任务，整理成可重复运行的版本。每个任务都要有固定仓库快照、初始需求、至少一次跨会话要求变化、明确的完成条件、可自动运行的测试和独立评分脚本。

任务示例：第一会话要求为模块增加一种行为；第二会话补充该要求只对某些输入生效，或从某个版本起生效；agent 需要检查已有实现，修改代码和测试，并确保旧行为没有回归。具体任务应按仓库实际功能编写，不能让答案从文件名或测试输出中直接泄露。

**对照条件：**先固定同一个 SWE-agent、模型和源码访问权限，比较“会话重置、仅保留代码工作区”和“会话重置、保留代码工作区＋显式记忆”两组。每次开启新会话都清空最近对话；另加不重置的完整历史组时，作为独立条件。每次运行都从相同仓库快照开始，条件间配对，运行顺序随机或预先平衡；每个任务、每个条件至少 3 次独立运行作为起点。3–5 个任务、2 条件、3 次重复共 18–30 条完整任务轨迹，不是 18–30 个独立任务。文件隐藏另按实验二定义，不能与源码不可读混在一起。

**记录内容：**每轮会话输入、记忆写入与检索、项目文件内容是否暴露、命令记录、代码 diff、测试日志、运行失败、最终仓库状态和人工修补情况。模型版本、调用参数和 API 路由也要记录。

**主要指标：**隐藏测试通过；回归测试通过；项目可构建；变更是否只影响要求指定的范围。辅助指标包括任务完成率、人工修补量、测试运行次数和耗时。agent 的自我报告不能代替测试结果。

**正式运行前验收：**接通真正的 SWE-agent 会话；验证会话确实重置而代码保留；验证显式记忆确实写入、取回、进入最终输入；隐藏评分器在 agent 运行期间不可访问。先用 1 个任务跑通两组作为流程检查，再冻结 3–5 任务的正式协议。流程检查不用于挑选有利结果。

**与实验三结合：**真实仓库任务出现失败后，使用保存的检查点做单阶段修复与 sham 对照；修复之后继续让 agent 修改代码并跑测试。这样才能验证诊断出的原因是否影响真实项目结果。

**范围限制：**3–5 个任务、每条件三次只能说明流程可运行并提供初步证据，不能支持“agent 普遍具备 SWE 能力”。若要作更广泛结论，需增加独立仓库、任务类型和运行次数。

## 实验二：文件可见性与显式记忆

**问题：**项目文件能否帮助 agent？文件和显式记忆是互补、重复，还是都没有明显作用？

**实验结构：**采用 2×2 设计。同一任务、同一检查点下，对比四种条件：

| 条件 | 项目文件内容 | 显式记忆 |
|---|---|---|
| A | 可见 | 不提供 |
| B | 可见 | 提供 |
| C | 隐藏 | 不提供 |
| D | 隐藏 | 提供 |

先在同一检查点完成配对比较，确保四组的任务状态、请求、候选行为和历史来源相同；再按预先确定的条件跑完整任务轨迹，观察长期效果。隐藏文件条件仍保留执行环境和必要的任务接口，需明确它隐藏的具体内容。

**两类实验分开：**先在现有受控任务重做“文件内容是否进入决策模型”的比较；真实仓库任务仍需读取和修改源码，不能把整个仓库隐藏后继续声称测的是相同的代码修改能力。如果在真实仓库增加可见性对照，应明确只屏蔽承载历史需求的文件或通道，并单独命名、报告；代码、Git 历史、搜索、命令输出和摘要中的旁路泄漏也要检查。不能只设置 `workspace_files_visible=false`，却让 agent 通过 shell 读回同一内容。

**运行次数：**已有 6 个任务的一轮可见/隐藏结果作为初步数据。先固定显式记忆条件，做 6 任务×可见/隐藏 2 条件×3 次独立重复，共 36 条新轨迹；若扩为完整四条件，共 72 条新轨迹，其中可复用协议完全相同的前两条件。然后增加新的独立任务实例。重复次数不能替代任务数量，最终规模要根据初步波动和可用预算确定。

**主要指标：**现有受控任务报 checker 动作准确率、分条件准确率、cycle/drift 和终局通过；真实仓库扩展报隐藏测试、回归测试和任务完成率，不能混用两种评分口径。同时报告每个任务的可见减隐藏差值和不确定范围。分析记忆收益时，分别比较可见文件下的 B−A，以及隐藏文件下的 D−C；两者差异用于判断文件和记忆是否互补。

**判定：**不要求可见与隐藏两组必须不同。差异稳定且跨任务方向一致，才支持文件有稳定作用；差异接近零则说明本实验没有发现稳定影响。若只有少数任务受益，应报告受益任务类型，不要概括成文件普遍有用或无用。

## 实验三：失败原因修复实验

**问题：**诊断出的失败环节，是否真的是任务失败的原因之一？修好它能否提高最终任务成功率？

**基本做法：**从实验一、二开始记录全过程并保存检查点。预先固定失败样本纳入规则，标出可复核的最早缺失阶段；不确定的样本单列，不强行归因。从该阶段之前保存的同一个检查点复制三个分支：原样继续、只修被诊断出的阶段、投入相近但不针对该问题的 sham 修复。之后让 agent 自己继续完成任务。

检查点必须同时保存代码工作区、显式记忆及索引、当前会话/工具状态、模型输入和相关配置；只重建初始 Git 版本不等于恢复失败前状态。先实现并验证这些快照，再做修复比较。

| 诊断出的情况 | 修复组 | 对照组 |
|---|---|---|
| 新要求没有被保存 | 补入缺失的新要求 | 补入等量、但与任务无关的信息 |
| 正确信息已保存，但检索不到 | 让检索阶段能取回该条信息 | 保持原检索结果，增加等量无关记录 |
| 正确信息已取回，但没有呈现给决策模型 | 把该信息放入最终决策上下文 | 放入等量无关信息，保持上下文长度接近 |

**控制要求：**三个分支使用同一模型、同一任务、同一检查点和同一后续执行流程；记录提示词、记忆内容、检索结果、最终上下文、代码修改和测试结果。修复组与对照组的 token 数、信息位置和记录数量尽量匹配。不能一次同时改存储、检索和提示词，否则无法判断是哪一步带来变化。

**主要指标：**任务是否完成；隐藏测试是否通过；回归测试是否通过。另报修复后下一步是否选对、错误是否从该阶段消失。只报告答案变对不足以证明真实任务改善。

**两阶段报告：**第一阶段可用 oracle 方式直接补齐缺失环节，测量“修好后最多能改善多少”；这只是诊断上限。第二阶段让 agent 自己按诊断结果实施修复，再测一次，判断该修复方法是否可用于真实系统。

**判定：**只有修复组相对于 sham 组，在多个任务和重复运行中持续提高最终任务成功率，才支持“修复该环节能改善表现”。若只有 oracle 修复有效，结论应限于“该环节可能构成瓶颈”，不能说系统已能自动诊断并修复。

## 执行顺序

| 顺序 | 工作 | 通过标准 |
|---|---|---|
| 1，优先 | 接通 SWE-agent 和记忆，在 1 个真实仓库任务上验证跨会话流程，再运行 3–5 任务两条件实验 | agent 确实修改仓库；重置、记忆、独立评分器和完整日志均有效 |
| 2，与 1 同属首批 | 重做受控任务的文件可见/隐藏：先两条件重复，再扩展文件×记忆四条件 | 实际输入/工具访问证明屏蔽生效；同任务配对，报告差值和波动 |
| 3，紧随其后 | 对前两组中的失败做原样继续、单阶段修复与 sham 比较 | 同一失败前检查点分支；只改目标环节，比较最终执行/测试结果 |
| 后续，暂缓 | 修正旧候选措辞后的完整主实验重跑，以及旧系统总排序扩展 | 将来若重新使用这类强结论，再补相应有效性与重复验证；不阻塞本轮三组 |

新文件可见性运行如复用候选接口，应使用真实、中性的候选说明并核对 checker；这是该实验自身的接口检查，不要求先把旧主实验全部重跑。新协议、旧协议结果分开报告。冻结版本、模型、请求和日志是每组实验的必要准备，不另行变成“大规模主实验重跑”的前置阶段。

## 本轮结论能说到什么程度

- 阶段修复有稳定收益：可以说相关诊断能指导有效干预；若只做 oracle 修复，则只能说该环节可能是瓶颈。
- 文件可见与隐藏有稳定差异：可以在已测任务和配置范围内报告文件的作用；没有差异也应如实报告。
- 真实仓库实验成功：可以说跨会话要求遵循影响了实际代码修改和测试结果；任务少时须明确这是初步证据。
- 三组结果都完成后，仍不能自动推出对所有软件工程任务、所有 agent 或所有项目文件都成立。
